# AlgoOS 第二次阶段汇报方案

建议 **11 页正文、2 页答疑，正文约 8–10 分钟**。沿着「现实问题 → 为什么选在线评测 → 系统怎么跑 → 实测证明什么 → 接下来怎么测」讲。目标是让导师能复述你们的研究问题，并看懂这次验收的边界。

## 进度怎么说

推荐直接说：「**N1–N3 的本机核心链路已验证，N4 已通过本机交接预演，下一步是独立复现、部署和性能对照。**」若被问百分比，可以说「**按本轮 N1–N4 的交付范围，粗估约三分之二（65% 左右）**」，并说明这是团队对阶段工作量的估计。它不是测试通过率，也不包含总案里所有扩展功能的完整实现。

| 范围 | 现在能确认的事情 | 剩余工作 |
| --- | --- | --- |
| N1：单机基线 | N1.1–N1.5 本人通过 | N1.6 仍待独立复核 |
| N2：统一协议 | v1 契约和 Python/C++ 往返已验收 | 随部署继续确认端到端兼容 |
| N3：本机分布式链路 | 本机提交、编译、两节点执行、汇总、同节点重投与去重通过 | 生产隔离与真实 OOM、常驻服务及长期失联转派仍有待验收项 |
| N4：交付与实验 | 交接包已由系统负责人在仓库外重新构建并复跑 | 应用负责人独立复现；确认云环境、按角色部署、固定负载采集与分析 |

系统侧现在还可以准备交接版本、实际接口与常驻服务的最小入口、节点配置和实验数据采集方式；应用负责人可先独立复现，并接手结果展示。云端验收需要实际节点条件。详见[当前状态表](../tasks/system/new_plan_1110.md)和[应用交接入口](../ops/deployment.md#n4-应用负责人接手入口2026-11-15)。

## 一天内的 Web 演示范围

**一天内值得做的是本机单页演示。** 优先把已跑出的真实验收数据展示出来：顶部选提交，下面显示提交编号、编译/最终状态和派发数量，再按测试点列出判定、执行节点与原因。用本人复跑的 `correctness.csv` 和 `replay/manifest.json`；在页面标注「本机实测记录回放」。用 AC、WA、CE、SE 四个样例验证，CE/SE 页面应明确显示未派发。

时间分配：前半天完成单页、接入真实证据并复核；后半天预留联调、录屏和排练。若还有时间，可加一个仅在本机运行的「运行内置样例」按钮，把现有批次跑出的结果载入页面。这部分是加分项，只有按钮实跑通过后才在台上演示。当前有 Python 提交/查询函数和一次性验收入口，尚无正式 HTTP API 或常驻服务；一天内不把任意代码公开提交、登录或云部署列为交付条件。

汇报中把它称为「**评测结果演示页**」。如果只做到回放，就展示真实历史结果；如果本机按钮通过，就演示内置样例运行；若页面联调不及，直接用同一份四行对照表和终端录屏。三种版本共用同一个讲述顺序。

## 正文页序

| 页 | 标题 | 核心内容与画面 |
| --- | --- | --- |
| 1 | AlgoOS：有限算力下的分布式评测实验平台 | 一句阶段结论：已在本机打通双节点评测与回传，准备交接和性能对照。 |
| 2 | 集中交卷时，等待从哪里来？ | 校内赛末场景；用「提交集中到达 → 排队 → 出结果」示意长短任务混合，注明是示意而非实测。 |
| 3 | 为什么用在线评测研究调度？ | 编译先完成，测试点可分别运行，最终结果可按标准答案核对；因此能同时测时间与判定是否一致。 |
| 4 | 一个节点与两个节点，怎么比？ | 固定提交轨迹、题包、时限和资源预算，问加节点何时减少等待，何时被通信与存储开销抵消。明确是研究问题。 |
| 5 | 本阶段系统结构 | 一张图画控制端、编译端、两个评测节点；队列传任务、对象存储放文件、数据库记状态。标注「同机两个逻辑节点」。 |
| 6 | 一次提交怎样走完？ | 用 A+B 串起提交编号、编译一次、生成两条评测任务、执行、汇总查询；语法错误分支直接 CE。 |
| 7 | 测试点分发与结果汇总 | 用 01、02 到两个节点说明顺序发布和轮询分配。回传先后可变，收齐后才写最终判定。 |
| 8 | 断线重投与去重 | 画两格：未 ACK 的任务由同节点重收；重复结果不多计。长期失联转派尚未验收。 |
| 9 | 四类实测判定 | AC、WA、CE、SE 四行小表，派发数 2 / 2 / 0 / 0；SE 是本次源码哈希校验失败用例，务必写明。 |
| 10 | Web 演示：一份提交怎样显示结果？ | 先展示 AC 的两条节点结果，再切到 CE 说明没有评测任务。备注「本机实测记录回放」或「内置样例现场运行」，按实际完成内容选。未完成则用截图/录屏替换。 |
| 11 | 交接与下一轮实验 | 说明源码包已在仓库外复跑，应用负责人待独立复现。固定条件下先比较节点数，再比较调度策略；报告吞吐和 p95 出结果时间。本阶段没有提速结论。 |

答疑页备两张：**完整链路与 v1 字段**（提交号、测试点号、内容哈希）；**实验矩阵和待验收清单**（单/双节点、固定预算、等待和周转时间、跨机与生产隔离）。技术图重画成当前实现，不直接截图目标 UML。现场演示控制在 60–90 秒，预录一遍作备用。

开场参考：「一场校内竞赛快结束时，多份程序可能同时提交。短任务也会排队。我们想知道，在算力有限的情况下，把编译和评测分开、把评测分给多个节点，什么时候能让人更早拿到结果。今天先展示这条链路跑通了什么，以及我们怎样确认拆分后没有判错。」

结尾参考：「目前是在同一台机器上验证双节点协作、判定一致和重复结果不多计。下面会在统一条件下测量吞吐和尾延迟，再判断扩节点与改调度各能带来什么收益。」
