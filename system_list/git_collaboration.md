Q：所以，你所说的关键节点，如果我们按照一天的工作量来计算，就是开工、开始新任务前，pull；收工，push吗？是不是PR、merge最好也是每天操作一遍？（在确保我们三个现在都可以开始推进的情况下）

A：**基本可以这样理解：开工时检查并更新，收工时提交并推送；PR 和合并按任务完成情况进行。**

建议你们采用下面的节奏：

| 时间或条件 | 要做什么 |
|---|---|
| **每天开工** | 检查当前分支和未提交改动，查看 `main` 是否有更新；有需要就 Pull 更新 `main`，再合入自己正在开发的分支。 |
| **开始新任务** | 从更新后的 `main` 创建新任务分支。继续昨天的任务，就沿用原分支。 |
| **每天收工** | 检查差异，Commit 并 Push 当天改动；未完成的内容注明状态。没有新改动就不用提交。 |
| **小任务验证通过、可以交接** | 当天发起 PR，队友检查后尽快合并。 |

**PR、合并不用强制每天一次。** 一项任务做两天，可以每天 Push，第二天验证通过后再 PR；当天完成了可以交接的小任务，就当天 PR。合并以检查通过为条件，不必等到晚上。

三人都开始推进后，尤其要**优先合并其他成员马上要用的成果**。例如：

- 你的运行模块完成验证，就准备 PR，让队友取得它。
- 应用队友完成正式题目包，就准备 PR，供你接入评测。
- 算法队友完成可验证的 FCFS 小任务，也可以单独交接。

另外，两个合并方向要分清：

- **`main → 自己的分支`**：开发中接收团队更新，按需进行。
- **`自己的分支 → main`**：通过 PR 交付成果，验证和复核后进行。
